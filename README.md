# Яндекс Пэй → Excel (Chrome extension)

Расширение для Chrome/Яндекс Браузера: выгружает историю операций с `bank.yandex.ru` в настоящий `.xlsx` — без копирования, скриншотов и сторонних сервисов.

Проект распространяется по лицензии [MIT](LICENSE).

## Установка

1. Откройте `chrome://extensions/` (в Яндекс Браузере — `browser://extensions/`).
2. Включите «Режим разработчика».
3. Нажмите «Загрузить распакованное расширение» и выберите папку `src` в репозитории (в ней лежит `manifest.json`).
4. Закрепите иконку на панели.

Для установки из исходников сборка не нужна: в проекте нет зависимостей и не требуется `npm install`. Собрать релизный архив можно командой из раздела «Сборка».

### Из релиза

1. Откройте [страницу релизов](https://github.com/pravets/yandex-bank-exporter/releases) и скачайте `yandex-pay-export-<версия>.zip`.
2. Распакуйте архив в отдельную папку: `manifest.json` лежит в корне, рядом только файлы расширения.
3. Загрузите эту папку через «Загрузить распакованное расширение».

Рядом с архивом публикуется `SHA256SUMS`: положите его рядом с архивом и сверьте командой `sha256sum -c SHA256SUMS` (на Windows — `certutil -hashfile yandex-pay-export-<версия>.zip SHA256`).

## Как пользоваться

1. Откройте `https://bank.yandex.ru/my/history` и войдите в аккаунт.
2. Нажмите на иконку расширения.
3. Выберите период: текущий год, прошлый год, всё время или свой диапазон.
4. «Скачать Excel» — файл `Яндекс_Пэй_<период>.xlsx` окажется в загрузках: `Яндекс_Пэй_2026.xlsx`, `Яндекс_Пэй_2025.xlsx`, `Яндекс_Пэй_всё_время.xlsx` или `Яндекс_Пэй_2026-01-01_2026-01-31.xlsx`.

Границы периода считаются по московскому календарю, в какой бы зоне ни был браузер. Свой диапазон — это целые московские дни: от `00:00` выбранного дня «С» включительно до `00:00` дня после «По» не включая его. Поэтому последний выбранный день входит полностью, даже его последняя миллисекунда. Пустое поле оставляет границу открытой. Имя файла строится из тех же дат, сохраняет кириллицу и не содержит запрещённых файловой системой символов.

По умолчанию операции, оплаченные картой другого банка, в файл не попадают: они уже учтены в выписках этих банков. Включить их можно галочкой «Включать операции с карт других банков».

Если страница была открыта до установки расширения, попап предложит «Обновить страницу» — после перезагрузки запрос истории перехватится автоматически.

## Что внутри файла

- **Операции** — по строке на операцию: дата и время (МСК), месяц, описание, категория, тип, направление, сумма, баллы, кешбэк, карта/счёт, статус, ID операции. Автофильтр и закреплённая шапка.
- **Сводка** — итоги, разбивка по месяцам и категориям расхода.

Колонка «Направление» (`Списание`/`Поступление`) однозначно отделяет исходящие переводы от входящих: по ней отчёт можно пересчитать независимо, не угадывая сторону по типу операции.

Колонка «Карта / счёт» заполняется продуктом Яндекс Пэя из фильтров истории: `Карта Пэй`, `Счёт`, `Сплит` или `Баллы Плюса`. Если привязку найти не удалось, честно пишется `Не определено`, а число таких строк видно в шапке сводки и в статусе экспорта. Если банк принял только широкую форму фильтра продукта, привязка помечается как приблизительная, и её число тоже видно в сводке.

Операция без ID не теряется: дубликаты определяются по полному отпечатку записи (дата, сумма, направление, название, категория, статус), поэтому записи, различающиеся категорией или статусом, остаются отдельными строками. Число операций без ID и отброшенных дубликатов указано в сводке.

Если банк вернёт некорректную сумму, не-RUB валюту или битую дату, строка не превращается в ноль и не подменяется: она остаётся в листе со статусом «Некорректные данные», а в сводке появляется счётчик таких строк. В итоги они не входят.

Подпись `rightSubTitle` (`Карта · 0980`) — это карта оплаты, часто из другого банка, либо карта контрагента по переводу. К продукту Яндекс Пэя она отношения не имеет, поэтому в колонку «Карта / счёт» не попадает. Такие операции по умолчанию исключаются из файла: они уже учтены в выписках других банков. Галочка «Включать операции с карт других банков» возвращает их в отчёт.

Переводы между своими счетами вынесены в отдельный тип: иначе они раздувают «расходы» в разы. Галочка «Включать переводы между счетами» исключает именно внутренние переводы; обычные переводы контрагентам остаются в выгрузке при любом положении галочки. Операции в статусах «Ошибка»/«Отменено» попадают в список, но не в итоги.

## Как это работает

Страница истории — SPA, данные приходят GraphQL-запросом `GetTransactionFeedView`. Content script (`content.js`, MAIN world, `document_start`) перехватывает первый такой запрос и запоминает его тело: `agreementId` и хэш persisted query меняются между релизами банка, поэтому ничего не захардкожено — переиспользуется ровно то, что отправило само приложение.

Дальше попап листает ленту тем же запросом, подставляя `cursor`, страницами по 50 операций, и останавливается, когда лента ушла за начало выбранного периода.

Чтобы понять, к какой карте или счёту относится операция, попап берёт список продуктов из запроса `GetTransactionsFeedFilters` (Карта Пэй, Счёт, Сплит, Баллы Плюса) и листает ленту отдельно по каждому продуктовому фильтру. Операция помечается продуктом, если попала в его фильтр. Для перевода между своими счетами в колонке может оказаться два продукта через ` / `.

`.xlsx` собирается на месте: `lib/xlsx-lite.js` пишет OOXML и упаковывает его в ZIP методом STORE. Никаких внешних библиотек и сетевых вызовов, кроме `bank.yandex.ru`.

## Диагностика

Если банк меняет контракт, в подвале попапа появляется кнопка «Сохранить образец ответа для диагностики». Она делает один запрос общей ленты, берёт до 5 операций и сохраняет JSON в загрузки.

По умолчанию образец обезличен: остаются имена полей, пути, типы и названия GraphQL-операций, а суммы, номера карт, `agreementId`, тела запросов и балансы из фильтров замаскированы. Для полноценного разбора есть галочка «Полный образец»: она сохраняет реальные значения в файл с суффиксом `-full` и подписью в интерфейсе. Файл никуда не отправляется, его можно открыть и посмотреть, какие поля карты/счёта приходят от банка.

Если запрос пришёл в форме, которую перехватчик не разбирает (нестроковое тело), это видно в диагностике в поле `unsupportedForms`, а не теряется молча.

## Приватность и права

- `scripting`, `activeTab` — выполнить запрос истории в контексте вкладки банка.
- `downloads` — сохранить файл.
- `host_permissions`: только `https://bank.yandex.ru/*`.

Данные не уходят никуда, кроме самого банка: расширение читает ответ, который и так загружает ваша вкладка.

## Ограничения

- Работает, пока Яндекс не поменяет GraphQL-контракт; если запрос истории перестанет перехватываться, попап так и скажет.
- Перехватывается только `fetch`; XHR-запросы истории не поддерживаются. Если тело запроса не строка, перехват его не разбирает, но фиксирует это в диагностике.
- Каждый запрос к банку ограничен 30 секундами: зависший ответ завершается понятной ошибкой и освобождает попап, а не держит его до закрытия вкладки.
- Повторный экспорт или диагностика не запускаются, пока идёт предыдущая операция; блокировка берётся до первого ожидания.
- «Подготовить страницу» принимает только снимок, снятый после обновления и в текущем документе вкладки; данные прошлой загрузки не выдаются за готовность.
- Выгрузка делает отдельный проход по каждому продукту — это дольше одного прохода по общей ленте. Если банк не отдал список продуктов, карта/счёт останутся `Не определено`.
- Нужна открытая вкладка банка с активной сессией.
- Лимит — 400 страниц по 50 операций (20 000 записей) на каждый проход: общая лента и каждый продуктовый фильтр листаются отдельно, поэтому суммарный бюджет запросов больше. Если лента оборвалась по лимиту или курсор перестал двигаться, отчёт помечается как неполный: предупреждение видно в статусе попапа и в шапке сводки.
- Лента без прогресса курсора останавливается сразу, а не расходует весь лимит запросов на одну и ту же страницу.
- Легитимно пустая история продукта не расширяется до операций других счетов: альтернативная форма фильтра пробуется только при ошибке запроса.
- Глубина истории ограничена тем, что отдаёт банк; обычно это несколько лет.

## Сборка

Для запуска расширения сборка не нужна — Chrome загружает `src/` как есть. Сборка нужна только для релизного ZIP.

Требования: Node.js 24 (та же версия, что в CI). Зависимостей нет, `npm install` не требуется; `zip`/`unzip` тоже не нужны.

```bash
node scripts/build-extension.mjs                    # версия из src/manifest.json
node scripts/build-extension.mjs --version v1.3.0   # с проверкой соответствия тегу
node scripts/build-extension.mjs --out build        # другой каталог вместо dist
```

Скрипт:

1. проверяет формат версии (1–4 числа, каждое до 65535);
2. сверяет `--version` с `src/manifest.json` и падает при расхождении, называя обе версии;
3. проверяет, что все файлы, на которые ссылается манифест, существуют;
4. пакует `src/` в STORE-ZIP без `README.md` и служебного мусора;
5. перечитывает архив и сверяет имена, размеры и CRC32.

Результат — `dist/yandex-pay-export-<версия>.zip`. Дата записей в архиве фиксирована, поэтому один и тот же набор файлов даёт один и тот же SHA256. Получить справку по флагам: `node scripts/build-extension.mjs --help`.

## Выпуск релиза

Версия расширения живёт в одном месте — `src/manifest.json`. Порядок выпуска:

1. Поднимите `version` в `src/manifest.json` (1–4 числа, каждое до 65535) и закоммитьте в `master`.
2. Поставьте тег с префиксом `v` и отправьте его:

   ```bash
   git tag v1.3.0
   git push origin v1.3.0
   ```

3. Workflow `.github/workflows/release.yml` прогонит `node tests/run-tests.mjs`, соберёт `yandex-pay-export-1.3.0.zip` из `src/`, сохранит рядом `SHA256SUMS`, прикрепит оба файла к GitHub Release и положит архив в artifact сборки.

Тег обязан совпадать с версией манифеста: иначе сборка падает до публикации и называет обе версии. Предрелизные теги (`v1.4.0-beta.1`) допускаются — релиз помечается как prerelease.

Локальная сборка без GitHub описана в разделе «Сборка»: те же команды собирают архив, который workflow затем прикрепляет к релизу.

## Проверка

Требования: Node.js 24. Для независимого verifier дополнительно нужен Python 3 и пакет `openpyxl` (в CI он ставится явно); на Windows запускайте его с `PYTHONIOENCODING=utf-8`, иначе печать ₽ упадёт на cp1251. Без Python или `openpyxl` verifier пропускается, а не валит общий прогон.

```bash
node tests/run-tests.mjs
```

Один прогон собирает отчёт из синтетических операций и запускает отдельные наборы проверок: пагинация (причины остановки, повтор курсора, лимит, дедупликация), галочка внутренних переводов, контракт денег и дат, XML, блокировка повторного запуска, свежесть снимка `prepare`, обезличенная диагностика, перехват `content.js` и сборка релизного архива. Отдельно прогоняется календарный контракт в четырёх часовых зонах.

```bash
python tests/verify.py                     # проверяет tests/fixtures/sample-report.xlsx
python tests/verify.py путь/к/отчёту.xlsx   # проверяет любой отчёт
python tests/verify.py отчёт.xlsx tests/expected.json  # + ручные ожидания фикстуры
```

Verifier нужен `openpyxl` и читает отчёт независимо: сверяет все KPI сводки, строку «Итого», месяцы, категории и их доли, причём в целых копейках без допуска — расхождение на 0,01 ₽ проваливает проверку. `tests/expected.json` содержит ожидания для маленькой фикстуры, выписанные вручную, а не вычисленные из тех же преобразований расширения.

`tests/fixtures/sample-report.xlsx` — образец готового отчёта, пересобранный текущим генератором. Он позволяет проверить чтение книги без Node; при изменении формата его нужно пересобрать осознанно, иначе образец устареет.
